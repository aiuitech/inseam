# Connections

A **connection** is an edge owned by a node: the concrete, configured means of reaching one other party. Connections are where protocols, credentials, and capabilities live.

## Two kinds

- **Node ↔ node.** Carries the inseam protocol: address sync, discovery queries, and fetch routing. Both ends are inseam instances, inside the trust domain.
- **Node → host.** How a steward reaches a host it serves. For a local host this is a local protocol (filesystem, OS APIs); for a remote host it is the service's own protocol (Gmail API, IMAP, a REST endpoint…). Used to enumerate sources, extract envelopes, and fetch content on demand. The host is unaware of inseam either way.

External requesters ([access-control](access-control.md)) are neither: they don't hold connections into the network — they arrive through a node's [API](node-api.md) and stay outside it.

## Anatomy

Every connection specifies:

- **Protocol** — how to speak: for node↔node, the inseam protocol over the iroh transport (below); for node→host, a service protocol supplied by a [plugin](plugins.md).
- **Credentials** — OAuth grants, API keys, mutual keys between nodes. Held locally by the owning node, never synced.
- **Capabilities** — what the edge supports: read-only vs. read-write, sync-capable (node↔node only) vs. fetch-only, enumeration support, and whether it offers a **change feed** (FSEvents, Gmail history API, …) that lets [index maintenance](index-maintenance.md) run targeted sweeps instead of full ones.
- **Host-native exclusions** — the host's own vocabulary for what not to enumerate (`.gitignore` and path patterns for a filesystem; labels and queries for a mailbox), applied during enumeration so an excluded source never becomes an address ([ignore](ignore.md)).

Capabilities of node→host connections are published network-wide as stewardship records in the [roster](roster.md), so routing knows which stewards can serve (and write to) which hosts. Credentials never leave the owning node; the roster carries the *fact* of the connection, never the means.

## Every connection type is a plugin

Connection types register into the `connections` [seam](services.md): the filesystem and Google Workspace connections ship as linked plugins in the distributions, and every other service-specific type (Slack, a CalDAV server) arrives as a loaded [plugin](plugins.md). The iroh node↔node transport is a linked plugin too, on its own `transport` seam (settled below). Adding a new kind of host to the network means writing a connection plugin, not touching anything. A connection's capabilities — change feed, writability — surface as capability facts consumers branch on ([kernel](kernel.md)).

Node↔node connections authenticate by mutual proof of the peers' keypairs — a node's identity *is* its public key, distributed via its [roster](roster.md) node record.

## Node↔node transport: iroh

The flagship node↔node connection plugin is built on **iroh**: QUIC dialed by the peer's public key, with NAT hole punching and encrypted, stateless relay fallback. Its model matches the roster's assumptions one-to-one — iroh's NodeId *is* the roster's node id, and its node-address info (relay URL + direct-address hints) is what a node record's endpoints field carries. This buys the miserable, undifferentiated problems — path finding, NAT traversal, relaying — from a wire-stable library, instead of spending our novelty budget on plumbing.

The network runs its **own relay**, typically on the always-on backbone node ([network](network.md)), rather than depending on public relay infrastructure. The bet is contained by the seam: iroh is one connection plugin, and swapping transports can never touch a consumer.

HTTP remains at the node [API](node-api.md) boundary for external requesters — that's a different door, not a node↔node transport.

## Paths not taken

- **libp2p.** Built for open networks of anonymous millions: transport negotiation, DHTs, gossip peer-scoring — modularity we'd pay for forever, solving problems a closed trust domain of tens of nodes doesn't have, with weaker NAT traversal than iroh in practice.
- **A mesh VPN (Tailscale/WireGuard) as prerequisite.** Solves reachability well but as an environmental requirement; inseam must work as self-contained node software. Users may of course run nodes over one.
- **A message broker (NATS/MQTT).** A central rendezvous contradicts the no-central-authority stance outright.
- **Hand-rolled transport.** Dial-by-key with traversal and relays is years of work orthogonal to inseam's actual contribution; the connection seam means adopting it costs no architectural freedom.

## Settled since

- **The seam is a registry, and it is plural.** A node stewards many hosts at once, so `connections` (the seam key; the singular `connection` was a single binding and therefore a single host per node — the first architecture's hidden assumption) is a registry provider in the spirit of `transforms`: every connection plugin, linked or loaded, registers one `Registration` per host it reaches as a fiber effect — host description (id, kind, display name), declared `Capabilities` (enumerates, change feed, writable), and the `Connection` handle — and unmounting the plugin unwinds it. Consumers resolve by host: the sweep by the host a `SweepRequest` names, operations by the host in an address. A registration is exactly the stewardship record the [roster](roster.md) will publish, minus credentials, so the roster work is a sync of what the registry already holds. One node holds **one connection per host**; a second registration for a stewarded host fails that fiber alone, by name. *Rejected:* realms (one `connection` key isolated per subtree) — they would answer "several hosts" but not "which host does this address belong to", which the registry answers directly.
- **Scopes name their host.** `IndexRequest`/`SweepRequest` carry a host id; `inseam index` accepts `--host` or an address (`inseam://<host>/<root>`), and a bare scope is accepted only while exactly one host is mounted — the moment there are two, naming is required, never guessed. The filesystem connection accepts a locator as a root (rooted at `/`), so the address form and the path form name the same scope.
- **A host's folders are its configuration, and they bound its scopes.** "Which folders does this machine index" belongs to the filesystem connection's entry (`fs.roots`), not to a transport flag: it is what an owner means by configuring local indexing, it lives in the composition beside the ignore rules that shape the same walk, and every GUI edits it through the settings projection. The list does double duty. Empty, it changes nothing — a scope is named per run and any directory is one, the CLI's `inseam index <dir>`. Non-empty, it is a bound: the connection refuses any scope outside its folders, by name, for every transport alike, so the console cannot widen what the owner chose by naming a path. The connection reports its folders with its registration (`Registration::roots`, surfaced as `HostView::roots`), which is how the web transport admits a folder as an index root without accepting a path of its own: the request's `root` must equal, verbatim, a folder some host reports. `--index-root` stays as the transport-level allowlist for a hosted node whose operator wants the owner never to name paths; the two compose (either admits a request) rather than replace each other. *Rejected:* an index operation with no scope that sweeps every configured folder (a later convenience, not the bound itself), and a walk that starts from all roots at once (one scope per run keeps reports and budgets legible).
- **OAuth is a seam, not a connection.** "A generic OAuth connection" cannot enumerate anything — Gmail's sources are messages, Drive's are files — so the reusable part is the *credential*, and it is the `oauth` seam ([services](services.md)): a grant is one record (authorization and token endpoints, scopes, which environment variables hold the client id and secret), the linked `oauth` provider runs the authorization-code + PKCE flow (RFC 6749/7636), keeps tokens in owner-private credential files under the node's data directory, and refreshes them ahead of expiry; a host connection consumes a grant by id and asks the handle for a live access token. This is also the attenuation point for loaded connections: a bridge can hand a component a handle that authorizes requests without ever revealing the token. *Rejected:* a per-plugin OAuth implementation (every service connection would carry the same flow and its own token file format), and keeping refresh tokens in the kernel's `state` namespace (credentials never enter the store — [kernel](kernel.md)); the data directory gained a plugin-visible path (`ApplyCx::data_dir`) for exactly this class of file. A grant whose client variables are unset is held `MissingSecret` rather than failing the whole `oauth` fiber, so one unconfigured provider never parks the others — a deliberate, per-grant reading of the "missing secret parks" rule ([composition](composition.md)).
- **The oauth seam is a registry too; the connection that knows its provider brings the grant.** Configuring Google's endpoints and seven scopes by hand in the `oauth` entry was the hidden cost of "grants are configured once in the composition": every owner would copy the same block from the docs, and whole-config replacement ([composition](composition.md)) meant a settings UI that re-saved the `oauth` entry silently dropped it. So a grant arrives through either door — the `oauth` entry for a provider nothing knows yet, or a connection plugin's `register_as_effect` for the provider it is built for — into one registry with one rule (one grant per id, named loudly on collision), exactly the shape `connections` and `transforms` already settled on. "Adding a new kind of host means writing a connection plugin, not touching anything" now holds for OAuth-backed hosts: the Google connection is one entry, enabled in the base composition, and the owner supplies only the client identity through the environment. *Rejected:* presets inside the oauth plugin (`preset = "google"`) — the provider knowledge belongs with the connection that uses it, and it would still have needed an oauth-entry edit per account.
- **The redirect is the transport's choice, not the seam's.** A node the owner reaches remotely (the hosted web console) cannot take the redirect on its loopback — that is the browser's machine, not the node's. So `authorize` takes a `Redirect`: `Loopback` (the provider listens on `127.0.0.1:<port>/callback`, RFC 8252 — CLI, native app) or `External { redirect_uri }` (the transport serves the URI and delivers the browser's return through `complete_authorization`; the HTTP transport serves `/api/v1/oauth/callback` at its public URL). Both name the attempt by its CSRF `state`; `await_authorization` waits on either. The owner operations carry exactly this shape, so every client — CLI, macOS app, web — is the same thin skin over one flow, and a grant authorized from any of them is authorized for all. *Rejected:* pasting the code back by hand for the remote case (an owner surface that copies secrets through a text field), and a relay through the CLI (two processes to keep in sync for a one-time sign-in).
- **Grants announce their changes.** Authorizing or revoking fires `GrantChanged` on the kernel bus with the new state — including the signed-in account, read from the provider's OpenID `id_token` when its `email` scope was granted (no signature check: the token came straight from the token endpoint over TLS, and it names the account, it grants nothing). Connections behind a grant register and unregister their hosts on that event, so a long-running node gains its Google hosts the moment the browser comes back, without the kernel restarting anything. *Rejected:* a userinfo call at apply to learn the account (a network call at boot, and a node offline at boot would park the connection), and re-providing `oauth` to trigger consumer restarts (a restart of every connection to change one).
- **The OAuth client is the app's identity, not the user's — bring-your-own now, a bundled default later.** A client id/secret names *inseam* to the provider; the tokens it yields belong to whoever ran the flow (the owner's node) and never reach the client's creator, and the grant gives the creator no access in return — the only coupling is lifecycle (scopes, branding, verification, the power to disable) and aggregate usage counts. So there is nothing improper about every node using one inseam-owned client, and for Google's *Desktop* client type a distributed secret is non-confidential by design (RFC 8252 §8.5; PKCE carries the protection) — what rclone and gcloud ship. Two things stop us shipping one today: Google's verification (`gmail.readonly` and `drive.readonly` are restricted scopes — a client in Testing status caps at 100 users and expires refresh tokens after seven days, and publishing needs app verification plus an annual CASA assessment; calendar/contacts/tasks are merely sensitive), and blast radius (a suspended shared client disconnects every user at once; bring-your-own fails per user). So the path is: **bring-your-own is the always-available door** (`client_id_env` / `client_secret_env`, the one-time console step the docs walk through), and **when inseam is commercialized a verified inseam client ships bundled** and is the default when the owner has set no client — the `MissingSecret` state then arises only for explicit overrides. The bundled client is a *Desktop* client (any loopback port, no registered URIs) and therefore covers the CLI and the native app; a node authorized from the web console needs an exact redirect URI registered, so self-hosted web nodes keep bringing their own Web client, and the commercial hosted node owns one under our domain. *Rejected:* a central callback broker relaying codes to nodes (a new trust surface and a central service, against the no-central-authority stance), and shipping an unverified default (seven-day token expiry would look like a bug to every user).
- **The first remote connection is Google Workspace, one host per service.** A Google account is five hosts, not one: each service is a locator-schema family (a Gmail message id, a Drive file id, a `calendar/event` pair), which is what a host *kind* is ([roster](roster.md)), and a Gmail account stewarded by two nodes must be one `gmail` host. Ids are derived, never configured: `derive_host_id(kind, principal)` is BLAKE3 over the kind and the account address — the first connection to honor the addressing rule; the filesystem connection, which predated it with `fs-<hostname>`, now derives the same way from machine identity ([addressing](addressing.md)). Every service is read-only and is served as text where its sources have no byte form of their own (a message, an event, a contact, a task render as `text/plain` because that *is* what the connection serves); Drive serves files as their bytes and Docs/Sheets/Slides as their export. Enumeration has a ceiling everywhere: pages, sources per service per run, Drive folders, Gmail's per-message metadata calls in flight. Change feeds (Gmail history, Drive changes) are declared capabilities for when the scheduling hook exists.

- **The public web is one fetch-only host, and contacting it is opt-in.** A link inside an indexed document needs somewhere to point: a `web` host of kind `web`, whose locators are URLs and whose id every node derives alike (`derive_host_id("web", "public")` — there is one public web, so a reference minted on one node names the same thing on another). It declares `enumerates: false`: nothing on it is ever a source of this node, it is never swept, and it never makes a bare scope ambiguous — `resolve_default` considers enumerable hosts only, and naming it as a scope is refused by name. It grew the connection seam one method, `describe(address)`, so a fetch-only host can answer "what is this?" from headers before anyone reads bytes. Mounting it is the owner's consent for the node to contact linked sites, so it is absent from the base composition. Its fetch path is the node's SSRF posture: a node holds personal data and, hosted, sits beside internal services, so every hop — redirects included, followed by hand under a ceiling — resolves its host first, refuses any non-public address unless the owner named that host in `allow_hosts`, pins the connection to the addresses it checked, caps the body before and while reading it, and times the whole request out. *Rejected:* one host per origin (dynamic registrations the registry is not built for, and the allow list already scopes reach); caching fetched bytes in the node (the index holds references, never copies — [addressing](addressing.md)); trusting reqwest's redirect handling (each hop must pass the guard, and a redirect into a private range is the classic escape).

- **The node↔node edge is the `transport` seam, not a `connections` registration.** The `connections` registry answers one question — which host does this address belong to, and through which handle — and its entries are hosts, resolved by host id, one per host. A peer node is not a host: it has no locators, no envelopes, nothing to enumerate, and a registration for it would answer none of the questions consumers ask of one. So node↔node is its own seam, `transport` ([services](services.md)): dial a peer by node id and roster endpoints, name the protocol, get one exchange back, and register a handler per protocol as a fiber effect. A `node` seam beside it holds the identity the transport dials with — the keypair, minted once into the data directory and never configured — so the transport, the roster, and sync read one key instead of each keeping a file. *Rejected:* registering the transport into `connections` as if a peer were a host.
- **One ALPN, a protocol name per stream.** Every inseam connection negotiates `inseam/1`; each QUIC bi-stream opens with a JSON header naming the protocol it speaks (`inseam/sync/1`, `inseam/route/1`), and the transport dispatches to the handler registered under that name. One ALPN because a session must serve several protocols in both directions over one connection — a laptop's standing connection carries the backbone's sync exchanges and its routed reads alike — and because iroh already authenticated the peer's key in the TLS handshake, so the protocol has no business in the handshake. A version lives in the name; a breaking change is a new name, never a second ALPN. Bodies are raw bytes behind a length prefix, bounded at the fetch limit plus framing (40 MiB), since a base64 fetch inside JSON would not fit. *Rejected:* one ALPN per protocol (a connection per protocol, and a NAT binding per connection to keep warm).
- **Admission is the first stream.** A dialer's first stream is `inseam/hello/1`, carrying an invitation token or nothing; the acceptor asks the admission policy the roster installed and either admits the connection into its session table or closes it with a refusal code that says nothing more. The transport holds no membership knowledge of its own — with no policy installed it refuses everyone, so a node whose roster has not come up is closed rather than open — and the dialer needs no check, because iroh proved the dialed key. *Rejected:* checking membership on every request (admission is a property of the connection: a session either was admitted or does not exist).
- **`relay = "n0"` out of the box; the backbone's own relay is the recommended shape.** NAT traversal must work the first time two laptops meet, before anyone operates infrastructure, so the transport defaults to iroh's public relays. The moment a network has a backbone, the right shape is the one the [roster](roster.md) already describes: an iroh relay beside that node and every transport naming its URL, so no traffic depends on public relay infrastructure. `"none"` exists for a LAN or a test. The relay is packet plumbing either way — encrypted bytes pass through; nothing lands or is readable ([network](network.md)) — so the default costs no confidentiality, only a dependency the owner can drop by naming their own. *Rejected:* no default relay (the first join fails behind most home routers), and an address-lookup service (the roster is where endpoints come from; nothing about a node is published outside the network).
- **The endpoint vocabulary is the transport's, opaque to the roster.** A node record's endpoints are strings the transport renders and parses — `relay:<url>` first, then `ip:<socket address>`, loopback and link-local kept only when nothing routable exists, at most sixteen. The kernel bounds and stores them; only the transport reads them, and an unreadable kind is skipped with a warning so a newer transport's hint never breaks an older peer.
- **Sessions are symmetric, and liveness is a session.** Either side opens streams on a connection whichever side dialed it, and a request reuses the live session in either direction before dialing — which answers the symmetry question below with yes, and is what lets a dialable backbone reach an outbound-only laptop at all: the laptop keeps its connection open with a keep-alive, and the backbone opens streams on it. Two nodes dialing each other at once keep the connection dialed by the lower id, on both sides, so they converge. Liveness is learned by trying and never synced — `live` in an owner surface means a session is open or the last exchange succeeded — which is the health model routing consumes ([network](network.md)): a candidate with a live session is tried first, and every other candidate is tried.
- **The seam crossed the component boundary; the first loaded connection is a GitHub repository.** `connection-plugin` is the WIT projection of this seam ([plugins](plugins.md)): a component configures from its entry, describes its host by kind and principal, exports its edge capabilities, and enumerates, reads, and describes through locators of its own — reaching its service only through the node's guarded `fetch` under the hosts its manifest names. The bridge registers it here exactly as a linked connection: the host id is derived, the kind must be the manifest's, effective capabilities are declared AND exported, and one node still holds one connection per host. The instance is long-running (a cursor survives between calls), and `locator_prefix` — synchronous on this seam — is answered from what the component reported at its last enumeration of that scope, since the instance sits behind an async lock. `plugins/github` proved it: one repository as a host of kind `github`, one tree call per enumeration, raw reads at the configured ref, and a private repository through an entry-named OAuth grant whose bearer the bridge attaches. OAuth crossed as attenuation only — a loaded connection never sees a token, and cannot yet register a grant spec of its own (open below).

## Open questions

- The change-feed API behind the `change_feed` capability: the registry declares it today; the scheduling hook that turns a feed's hints into targeted sweeps is unbuilt ([index-maintenance](index-maintenance.md)).
- Writable Google edges (send mail, create events) once writability has a consumer; today every Google host is `READ_ONLY`.
- The bundled inseam Google client: which scopes it is verified for first (the sensitive-only set could ship before CASA clears the restricted Gmail/Drive scopes, with those two behind bring-your-own until then), and how the `google` entry expresses "bundled default unless overridden".
- Whether a loaded connection may register an OAuth grant spec (as the linked Google connection does) instead of consuming one the owner configured on the `oauth` entry.
- Connection liveness/health model and how it feeds routing decisions.
