# Indexing

How a node turns sources into a searchable **semantic graph**. The index is derived, local, and rebuildable ([discovery](discovery.md) states this); this doc is how it gets built.

## Fragments, not nodes

The graph's unit is a **fragment**: a piece of understanding derived from a source — a markdown section, a transcript line, a summary, an extracted entity. We deliberately don't call them "nodes": *node* already means an inseam instance ([nodes-and-hosts](nodes-and-hosts.md)), and overloading it inside the index would poison every conversation about either.

Every fragment carries:

- a **mimetype** — so the pipeline knows how to treat it next. `text/markdown`, `text/html`, `image/jpeg`, or inseam-defined types for derived things (a summary, an entity).
- **relations** — typed edges to other fragments, every one read **input → output** (the fragment a transform was applied to, to what it produced). Every emitted fragment relates to its input, and the kind says why. The kernel defines exactly two kinds — the **transform relation**: `contains` (structural decomposition) and `derives` (derived understanding, a summary). Every other kind is the emitting plugin's vocabulary: `links-to` (the markdown transform: a section to a URL it links), `mentions` (the entity extractor: a fragment to an entity), `transcribes` (the OCR plugin: an image to its transcript). Relation kinds are first-class — the [Finder](finder.md) weights them by name, and a kind it has never seen still conducts at a default weight.
- an **embedding** — every fragment gets one. A multimodal embedding model embeds whatever mimetypes it supports; text is the common case.
- a **content digest** — BLAKE3 over the fragment's content bytes, the key into the derived-artifact caches (below).
- an **extent** — where the fragment sits within its parent and how long it is (lines for text, bytes or timestamps otherwise). Extents are what let the [Finder](finder.md)'s `scan` operation peek into a slice of a source instead of fetching all of it.
- its source's **address** — and nothing more for access control: **authorization lives at the source level only.** A fragment is never more or less exposed than its source; boundary filtering resolves against the source's trust properties, and every fragment (summaries included) follows its source's answer.

Text fragments additionally enter the full-text index. The result per source is a tree rooted at the source, cross-linked into a graph by entity and link relations.

Fragments are index-local. They have no addresses, never sync, and two nodes indexing the same source will hold different fragments — that is the per-node asymmetry working as intended.

## Transforms

A **transform** is a registered handler: it takes a fragment of a mimetype it claims and emits child fragments with typed relations. Indexing is just recursive transform application until nothing claims the output (or budget runs out).

- A `text/markdown` transform decomposes by the document's own semantic structure: first-level headings with the text under them, second-level headings nested below, each `contains`-related to its parent. A link inside becomes a `text/uri-list` child.
- A URL fragment's transform may fetch the target — yielding a `text/html` child — whose own transform summarizes the page. Recursion, mimetype by mimetype.
- A `video/mp4` transform emits an `application/x-subrip` child, whose transform emits `timestamp:text` line fragments.

Every transform is a [plugin](plugins.md) registering into the `transforms` [seam](services.md): the universal ones ship as linked plugins in every distribution, and the long tail arrives as loaded plugins claiming emitted mimetypes — same registry, same claims/apply contract, with fetches going through capability-mediated I/O (a transform that follows links declares which hosts it may call; no raw sockets) and LLM budgets metered at the `llm` seam.

Two core transforms matter enough to name:

- **Summarizer** — attaches a summary fragment (the input `derives` it) to whatever it's pointed at, to a configured length. This is the one **mandatory** transform: the [Finder](finder.md) serves summaries in every response so an AI client can decide whether to keep digging, so every indexed source must have one. Profiles configure the length, not the existence. A small device's whole index can be summaries and nothing else.
- **Entity extractor** — pulls out people, places, projects, dates as **entity fragments**, deduplicated per index (one fragment per entity, however many sources mention it), with `mentions` relations back to every fragment that referenced it. Entities are the graph's connective tissue: they are how two unrelated sources end up one hop apart. Everything entity-shaped is this plugin's own vocabulary; what the kernel provides is the generic mechanism beneath it — **keyed fragments** (below).

Transforms are why unreadable data becomes findable: registering a handler for a mimetype teaches the whole network's indexes what that data means.

## Keyed fragments: the one index-wide fragment shape

A fragment normally belongs to exactly one source. The single exception the kernel's store supports is a **keyed fragment**: a fragment that belongs to no source and is deduplicated across the whole index under a plugin-namespaced key (`entity:person:greg`). A transform emits one as a **keyed sprout** — key, fragment, relation kind, and an **anchor** saying where in the emitting source the edge lands (the input fragment, or every source-content fragment whose text contains a needle, falling back to the input). The sweep resolves it: get-or-create the fragment under its key, then anchor it with the emitter's relation kind. A keyed fragment left with no relation is collected at the end of the sweep ([index-maintenance](index-maintenance.md)).

This is deliberately generic. Entities are the first vocabulary built on it; a topics plugin, a correspondent plugin over mail, a citation plugin over papers each bring their own key namespace, mimetype, and relation kind without the kernel learning any of them. Because keyed fragments belong to no source they carry no source address: they conduct relevance and appear in `expand`, but never rank as results themselves — boundary exposure stays source-level.

## Digests dedupe compute, not the graph

The expensive parts of indexing recur per fragment, not per source: embeddings, and the LLM transforms (summaries, entities). Fragment content digests turn those into **digest-keyed caches**:

- an embedding is stored once per `(content digest, embedding identity)` — the embedder model, its dimensions, and the vector scope; fragment rows reference it.
- an LLM transform's output is stored once per `(input content digest, that transform's shape-relevant identity and config)` — the same ingredients the shape stamp digests ([index-maintenance](index-maintenance.md)), so a shape change never needs a cache flush: stale entries simply stop matching.

The dedup is deliberately at the **artifact** layer, not the graph layer. Fragments stay per-source — every fragment carries exactly one source address, the invariant boundary filtering leans on — so the same file indexed from two hosts, or the same boilerplate section in fifty documents, still produces its own cheap fragment rows, but pays for its vectors and its LLM calls exactly once. The vectors are the storage bulk, so this is also where the index actually gets lean.

The same caches are what make the delete-and-rebuild maintenance model affordable: a rebuilt subtree re-runs decomposition (cheap) and hits the caches for every fragment whose content didn't change, so a rebuild costs only what actually changed. Cache entries left unreferenced by a rebuild or deletion are kept — content that comes back re-hits for free, the same tighten-then-loosen stance [index-maintenance](index-maintenance.md) takes on scope — and reclaimed only by the explicit `vacuum`.

## Configuration is composition

Everything above is configured per node by its [composition](composition.md), including what is kept out of the index altogether ([ignore](ignore.md)): which transform plugins are mounted and each one's config (summary lengths, entity budgets, recursion depth), which embedder provider runs, the sweep's cutoffs and budgets. A phone's composition: summarizer only, short summaries, vectors for summaries only, envelope-derived text, tight cutoff. A cloud node's: every transform, link-following, entities, long summaries, a vector on every fragment. Same machinery, different entries — the asymmetry [discovery](discovery.md) promises, with no profile mechanism separate from ordinary plugin config.

## Storage

The index lives in libSQL ([runtime](runtime.md)) as a single database file on the node's local disk — catalog tables and derived search tables in one file.

**The index is local storage; reach comes from the network.** An earlier cut of this design (the LanceDB era) kept an object-store backend open so a node could put its index on S3. That door is closed: remote storage pays round trips per probe — run from a laptop against a distant bucket, interactive queries degrade badly — and inseam already has a better answer for "limitless index off device": query fan-out. The small node keeps its lean local index and forwards queries to a big node whose index is deep; the big node keeps *its* index on its own fast local disk. Big index → big node's disk, reached over the network — never a far-away device mounting remote index storage.

## Paths not taken

- **"Transformer" / "transformation" as the term.** Rejected: *transformer* is unusably overloaded (the ML architecture — in an AI-native project, worst possible collision) and *transformation* names the event, not the registered thing. **Transform** (noun) keeps the intuition without the collision. Also considered: deriver, refiner, distiller — all narrower than what the mechanism does.
- **"Node" for graph vertices.** Rejected for the terminology clash above.
- **Fixed-size chunking.** Rejected as the primary decomposition: semantic structure (headings, subtitles, threads) produces fragments that mean something, which the relation graph and Finder depend on. A dumb chunker can still exist as a fallback transform for structureless text.
- **Entities as a separate store.** Rejected: entities are fragments in the same graph. One graph, one retrieval algorithm.
- **Shared fragment rows across sources.** Rejected: deduping identical content by making sources share subtrees would turn fragment→source into one-to-many and hand boundary filtering a new edge case, to save only the cheap rows. Dedupe the expensive derived artifacts by digest instead; keep the one-fragment-one-source invariant.

## Settled since

- **Where relations live physically**: the catalog tables hold the graph (fragments, relations, the keyed-fragment registry); the search tables in the same libSQL database hold vectors + FTS over text-bearing fragments and are strictly derived.
- **Incremental re-indexing, first cut**: change detection is `modified` timestamp + raw byte size, with an `indexed` completion mark so interrupted runs re-index; a changed source's whole fragment subtree is deleted (relations cascade) and rebuilt. The timestamp + size heuristic stays the *detector* — it needs no fetch — and the digest-keyed artifact caches (above) make its false positives cheap: a touched-but-unchanged file rebuilds structure and re-spends nothing.
- **Maintenance**: how the index stays true to sources and composition after the first build — the reconciling sweep, invalidation tiers, deletion handling, entity GC — is its own concept: [index-maintenance](index-maintenance.md).
- **Entity fragments and source-level authorization**: a deduplicated entity belongs to no single source, so entity fragments carry no source address. They conduct relevance and appear in `expand`, but never rank as results themselves — boundary exposure remains source-level. (Generalized since to every keyed fragment, above.)
- **Relation kinds are an open vocabulary, and entities are a plugin's.** The first cut had a closed `RelationKind` enum in the kernel (`contains`, `links-to`, `derived-from`, `mentions`, `transcribes`) and an entity registry the store and sweep knew by name. Both were plugin knowledge in the kernel: only the transform relation is a core truth of indexing — a transform always produces a child or a derivation — so the kernel now defines exactly `contains` and `derives` and validates every other kind as a name; the entity registry became the keyed-fragment facility and `EntityKind`, `ExtractedEntity`, `text/x-inseam-entity`, and `mentions` moved into the entity plugin. The one direction rule (input → output) replaced per-kind direction logic: `derived-from` (child → parent) became `derives` (parent → child) so the rule has no exceptions. *Rejected:* a relation-kind registry plugins declare into — kinds are data flowing through the fixed structure ([kernel](kernel.md)), and a registry would be a second source of truth for names that only the emitter and the finder's weight table care about.

- **The vector width belongs to the model; the config can only agree with it.** The embedder's `dimensions` is optional — unset takes the model's native width — and when set it is checked at activation against what the model produces: a built-in catalog of known embedding models first, the endpoint's own introspection second (a local ollama reports each installed model's capabilities and width through its native API; its OpenAI-compatible `/v1/models` lists ids alone), and explicit config last, taken on trust with the first embedding as the check. A smaller width is accepted only for Matryoshka-trained models and is then requested as the API's `dimensions`; every OpenAI-compatible server will truncate any model's vectors on request, and a truncated non-Matryoshka vector is noise wearing the right shape. *Rejected:* probing the model with a throwaway embedding on every boot (a network call per process start to learn a constant), and trusting the configured width until the first mismatch (the previous behavior — a whole sweep's transforms spent before the first batch failed).

- **Which fragments get vectors is an embedder dial, and part of the identity.** Vectors are the storage bulk, so `vectors = all | summaries` chooses between a vector on every text fragment and one bounded vector per source; every text fragment enters the full-text index regardless, so exact-term recall into sections survives the lean setting and only vector seeding narrows to summaries. The scope rides the embedding identity the store records, so flipping it is an in-place re-embed ([index-maintenance](index-maintenance.md)) — no transforms re-run — rather than a shape change that would rebuild subtrees. *Rejected:* a sweep-side row filter keyed into the shape stamp (re-runs LLM transforms to change what is derived from their output), and dropping non-summary rows from full-text too (saves little — text is already in the catalog — and loses exact-term search for a storage win that vectors, not text, deliver).

- **Local models are configuration, and the endpoint is asked what it knows.** A local ollama is `base_url = http://localhost:11434/v1` with an empty `api_key_env`; the `llm` provider reads its native discovery API beside the OpenAI-compatible one — installed models, which embed and which chat, each embedder's width — for `inseam models` and for width validation, and falls back to the plain `/models` catalog elsewhere. Thinking models are told how much to think per call (`transform_reasoning_effort`): transform-grade calls want the cheapest direct answer, and a thinking model left to itself spends its reply on thought and returns an empty summary. OpenRouter receives its native nested reasoning object with the unused trace excluded; other compatible endpoints retain the top-level `reasoning_effort` spelling. *Rejected:* an `ollama` provider variant (the seam contract is the OpenAI-compatible wire; the native API is discovery only, best-effort, and the plugin stays config-driven — `design/plugins.md`).

- **The batch lane is a run choice at the provider boundary, sized by parking the run.** Transform-grade LLM calls ride one of two lanes. The interactive lane answers each call with its own request. The batch lane parks calls and submits them together through the endpoint's batch API (OpenRouter's `/api/beta/batches`, at half price, with a 24-hour completion window) — the right trade for a large, time-insensitive indexing run and the wrong one for a few changed files, so it is chosen per transform (`summarizer.llm_lane = "batch"`) or per run (`inseam index --batch`), never by the model name alone. The endpoint plugin owns the lane: it declares a `transform_batch_model` fact (the transform model's `:batch` variant — the same model through another door), and a `:batch` request is parked by a background leader, never a caller's own task, which a cancelled planner would take down with everyone behind it. What makes a job large is the sweep: on the batch lane it plans `batch_concurrency` sources at once (4,096), every planner parks on its summary call, and the lane submits when the job is full (`batch_requests_max`, 5,000 for OpenRouter, or 64 MiB), when arrivals go quiet for two seconds, or when the oldest has waited two minutes; jobs run concurrently up to a bound, each item answers its own caller by stable id, and one failed item fails only its caller (who falls back to an extractive summary). OpenRouter values above 5,000 fail at boot instead of degrading a run after a rejected upload. Parking has a second edge: when the job lands, every parked planner resumes at once and reads its source, so the sweep gates source reads to `source_reads_in_flight_max` (128) in flight — 4,096 open files would exhaust a default 256-descriptor macOS shell, and the disk is no faster for being asked 4,096 times. The shape stamp names the base model, so changing lanes never re-indexes. *Rejected:* a `:batch` model name as the sole switch (the first cut — concurrent calls coalesced through a 50 ms window, so a job could never exceed the planning concurrency, eight requests, and the whole catalog waited behind a serial chain of tiny jobs); a two-phase sweep that plans everything, summarizes, then lands (a second pipeline whose partial state the landing order and the `indexed` invariant would have to reconcile — parking planners keeps one pipeline and one invariant); per-fragment batch files on disk (the provider takes the job inline and returns results inline; the bound is memory for the parked sources' content, which `batch_concurrency` sets).

- **Batch planning and source I/O have separate bounds.** A large `batch_concurrency` is needed to fill several provider jobs, but it must not become the number of files opened together. `source_reads_in_flight_max` caps content reads at 128 by default. A planner releases that permit as soon as the source bytes are in memory, before it parks on the LLM call. The endpoint retries 429 and server failures up to a fixed attempt limit, respects provider reset headers, and caps one retry wait at five minutes. A transient creation limit therefore delays a job instead of replacing all its summaries with extractive output.

- **Embedding requests are filled from larger store batches.** The request asks for `encoding_format: "base64"` — one packed little-endian `f32` array per input instead of thousands of decimal literals: less than half the bytes and a byte copy instead of float parsing on the hot path of indexing. The endpoint client packs 128 vector-covered rows per request. The store dispatches 256 search rows so summaries-only indexing of the source-plus-summary shape fills that request instead of sending it half empty; four batches run concurrently, bounding that shape at 512 vector inputs in flight. Servers that ignore the format parameter answer in floats and both shapes are read, so no endpoint is cut off by the optimization.

- **Indexing is a plan-then-land pipeline, parallel where the time goes.** Transforms — LLM calls above all — are the cost of indexing, so they are what runs concurrently: a configurable number of sources are *planned* at once (content read, transforms applied recursively, every claimant of a fragment in flight together), and each source's result is a pure-data **subtree plan** — fragments and relations by plan position, keyed sprouts with their anchors resolved — that the store *lands* in one transaction. Landing happens in enumeration order whatever order planning finishes, so the built index is independent of the concurrency dial; the embedding stage then embeds batches concurrently and lands them in order. The row buffer records each source's final-row boundary, so its `indexed` mark rides the first batch that contains all of that source's rows even when later sources remain buffered. Per-transform LLM budgets are shared meters with atomic reservation, so concurrency cannot overspend them. *Rejected:* per-fragment store writes as they happen (the first cut: one autocommit per fragment and relation, serialized with the transforms it waited on — a subtree rebuild scanned the vector table per source, and no amount of transform parallelism could hide the write path); per-transform or per-fragment parallelism inside one store transaction (the store is one connection, one writer — concurrency belongs in planning, not persistence); a work-stealing unordered landing (faster in the tail, but fragment ids would depend on timing, which golden checks and reproducible rebuilds are not worth trading for).

- **Fragments reference bytes; they never hold them.** A fragment's content is text or a **content reference** — the address of its bytes (`content_address`) — and the root's content is the source itself. This is the addressing stance applied inside the index: an image a document links to becomes an `image/png` fragment naming where the image lives, and the bytes are read through that host's connection exactly when a byte-wanting transform claims the fragment (the planner resolves the address through the connection registry, once per fragment, under the sweep's byte cap) or a client fetches it (`fetch_bytes`, which learns the content type from the referencing fragment when the address is no cataloged source). Bytes granted to transforms therefore stop being a root-only privilege: `wants_bytes` means the claimed fragment's bytes, whatever its depth, which is what lets an OCR plugin extend from image roots to linked images by claiming non-roots. Unreadable references (host unmounted, read failed, over the cap) degrade to a bare reference — still expandable and fetchable — never to a failed source. *Rejected:* storing referenced bytes in the index (moves data, and the cache of derived artifacts is keyed by digest anyway — [above](#digests-dedupe-compute-not-the-graph)); promoting every linked target to a source of its own (its host may not be enumerable, and a fragment of the linking document is where the relation and the source-level authorization already are); carrying the bytes inline in transform output (memory bound per parked source, and two tiers of transform would need two shapes).

- **The link follower emits references, typed cheaply first.** The `links` transform claims `text/uri-list` wherever it appears and turns a link to content on its follow list (images, by default) into a fragment of that type carrying a content reference to the link's web address, related `resolves-to`. The type comes from the URL's extension first — offline, deterministic, free — and from the resource's headers through the web host's `describe` when it is mounted and probing is on, the server's answer winning when they disagree and the extension's standing when the probe fails, so a site being down never un-links a document. Follow lists keep the graph from swallowing the web: an `html` link stays a link. The transform itself never opens a socket — the web host does, under its guard — and without the host it types offline and emits references a later mount makes fetchable. *Rejected:* fetching bodies in the transform (bytes belong to the planner's one read per referenced fragment, shared by every claimant); making linked images sources of their own (nothing enumerates the web, and the relation and the source-level authorization already live in the linking document's subtree); a linked-only follower (a `.uri` file at the root is the same claim).

- **The crawl depth is the sweep's dial, counted in reference hops.** Two followers that feed each other — links over `text/uri-list`, a page follower over `text/html` — would recurse into the web with nothing but the fragment depth and count caps in the way, and those are the wrong units: they bound a subtree's shape, not how far from the owner's data a chain has wandered. So the planner counts **reference hops** — content-referenced fragments in the chain from the source, itself included — and `sweep.max_reference_hops` (default 1: what a source links to, and no further) stops a chain past the cap by planting the reference but never following it: no transform is applied, no bytes are read, and the fragment stays expandable and fetchable, so the graph keeps the link it found. Transforms receive `reference_hops_left` so a follower can skip resolving a reference that will not be followed. The cap lives with the sweep's other shape dials and rides the shape stamp, because it is the sweep that recurses: a per-follower or per-host setting would hold only for the transforms that honor it, and a loaded follower cannot see the sweep's state at all. *Rejected:* a cap on the web connection (it answers fetches one at a time and cannot know where in a chain a request sits); dropping references past the cap (the link is still true and cheap to keep); counting hops per host (a chain that crosses from the web to a Drive file and back is one crawl).

- **Folders are sources, composed from their children, indexed leaves-first.** A directory is a source of type `inode/directory` (`source_type = "directory"`) with no bytes of its own: the sweep composes its content — a listing of its direct children with their names, types, and summaries, folders first (`inseam_seams::listing`) — from the catalog after those children have landed, and hands it to the transforms like any file. The summarizer reads it as prose, so a folder's summary is built from its children's summaries and never from their content; the `directory` structural transform parses it back into one `text/x-inseam-entry` fragment per child, related `contains`, carrying the child's name and type as text and its address as a content reference, so `expand` on a folder walks to what it holds. Entries are inseam-defined so no follower re-decomposes a child through its parent, and they carry the name and type only — repeating a child's summary under the folder would rank the folder beside the child on every query. Because the content is composed from landed state, the sweep is leaves-first across sources: every file lands, vanished sources leave, then folders run deepest level first, each level planned concurrently and landed in locator order, the same plan-then-land pipeline with the file pass's bounds. A folder's change detector is the listing's digest against the one its last run recorded — a directory's timestamp says nothing about what its children now summarize to — so a folder re-indexes when a child appears, vanishes, or re-summarizes, and hits the digest-keyed caches when nothing did. The filesystem host lists every directory between an admitted file and the scope root, the root included, so a folder exists in the index exactly when something under it does, and the sweep's ignore rules drop a folder with them when they keep out all of its files. Folders spend the deep budget like any source, after the files; one none of whose children is deep-indexed yet is cataloged only, which is how the cutoff and the budget reach it — it has no cutoff of its own. Folders have no addresses in flat locator spaces (Drive ids, mail), so only hosts with path locators produce them; `fetch` of a folder serves its name listing from the host. *Rejected:* a folder as a fragment (it has an address, the Finder returns addresses, and authorization is source-level); reading child content for the folder summary (the summaries are the point — a folder costs one transform pass, no host read); a store-reading transform (planning touches no store; the sweep composes, the transform parses); entries typed as the child's own mimetype with a reference (the link follower's shape — OCR would re-transcribe every image through its folder); the directory mtime as detector (it moves on rename, add, and remove, never on a child's edit); a per-folder cutoff (the children already answered to it).

- **The artifact caches are catalog tables, keyed by what changes the artifact and nothing else.** The embedding cache files one vector per `(text digest, model, width)`; the transform cache files one output per `(input digest, mimetype, root or not, entry id, shape fingerprint)` — the fingerprint already carries the transform model, so the key is the shape stamp's ingredients applied to one input. The vector scope is deliberately not in the embedding key: it decides which rows get a vector, never what the vector is, so flipping `vectors` re-embeds from the cache for free. The envelope hint (a file name) is deliberately not in the transform key: the summarizer reads it, but a renamed file with the same bytes wants the same summary far more often than a different one. Only an output the model produced is filed — the planner observes the granted LLM handle and files nothing for a fallback (budget spent, endpoint down) — because filing a fallback would make it permanent. Entries are first-writer-wins and kept until `vacuum`; a re-embed drops the search tables and finds its vectors still in the catalog. The planner's one store access is the cache read, before it applies an LLM transform; the outputs it produced ride the plan and are filed when the subtree lands, so planning still writes nothing itself. *Rejected:* keying vectors by fragment id (a rebuild assigns new ids — the whole point is to survive one); caching structural transforms (decomposition is cheap, and its output is regenerated by design); an in-memory cache (a crash or a second process would lose it — the index is the durable thing, so the cache lives in it).

- **Summaries are written to be found, and the cheapest summary is none.** The summarizer's ladder gained a top rung: text that already fits `target_chars` is its own summary (`via=verbatim`), because a model asked to shorten two sentences returns two worse sentences at a price. The LLM rung's prompt is reframed from "describe this document" to "write what someone would be looking for when this file is the right one" — a query-shaped paragraph in a searcher's words, with synonyms, which sits nearer to queries in embedding space than a précis does — and the same call returns the source's **keywords**, planted beside the summary as a `text/x-inseam-keywords` fragment for the full-text index, so the lean shape (summary only, no structural fragments) still matches the rare exact terms the prose left out. A verbatim summary plants no keywords — it left nothing out — and the benchmark bears this out: on NFCorpus with every abstract its own summary, keyword rows extracted from the text scored within a point of none, on either side, whichever way they were cleaned; beside the model's 400-character summaries the model's own keywords were neutral too (nDCG@10 0.3244 with, 0.3247 without). What moved the score was the summary itself: the reframed prompt at 400 characters reaches 0.324 against 0.288 for the old prompt at 200, and the whole abstract as its own summary reaches 0.330 at no model cost (`benchmarks/runs/beir-nfcorpus`). Keywords stay on by default because they cost one lexical row and no call, and their case — a rare exact term a summary omits — is one NFCorpus's topical queries never pose; a benchmark with identifier-shaped queries is the test that would retire or vindicate them. Before the call, a text past `llm_input_chars` is reduced without a model to the sentences that best represent it — terms weighted by frequency against their spread over sentences, one sentence per section first, then maximal marginal relevance until the budget is spent — so the model reads the whole outline instead of the first 8,000 characters; the same selection is the extractive rung, replacing "first words", and its weightiest terms are the extractive keywords. Every dial rides the shape fingerprint. *Rejected:* a sweep-level size floor below which structural transforms are skipped (the root fragment carries no text, so a source's text reaches full-text search only through its structural children — the floor would silently drop mid-sized sources from exact-term search, and the vector the duplicate row costs is free through the embedding cache anyway); keywords appended to the summary text (the Finder serves the summary to clients and `target_chars` bounds it, and a keyword list is neither prose nor length); keywords chosen by embedding candidate phrases against the summary's vector (one embedding per candidate, for a rerank over terms the model already named for free — worth revisiting only with a local embedder and a benchmark showing full-text recall still lagging); a third-party text-analysis crate for the selection (the one considered brought 25 dependencies and a hundred thousand lines for a few hundred lines of arithmetic).

- **Vectors are for prose.** A search row has a **role** — content, summary, or lexical — and the vector scope covers prose only: `all` is content and summaries, `summaries` is summaries. Lexical rows — keywords, entities and every keyed fragment, a folder's entries — keep their own full-text table too ([finder](finder.md)), and never carry a vector under either scope: full-text search matches names and terms exactly, the graph already carries an entity's relevance to everything that mentions it, and a vector over a list of names is a row of storage that buys no recall. *Rejected:* vectors on entities for fuzzy name matching (the query's own vector already reaches the prose that mentions the entity, and the entity edge spreads from there).

- **Plain text is an outline too.** `text/plain` roots go to the markdown transform, not the chunker: a `#` heading in a `.txt` file is the same outline, and a text without one falls back to the same paragraph chunking, so two handlers would agree on every input and differ only in name. Sections keep the root's mimetype. The chunker keeps the other indexable text — JSON, CSV, YAML, code — whose structure is not headings.

## Open questions

- Hierarchical summaries below the source: the summarizer's call now reads a model-free selection across the whole outline rather than the head (below), so a long document's tail is represented, but at one sentence per section. Section summaries built leaves-first and rolled up into the document's — the folder move one level down — would cover each section properly at the cost of one call per section; the listing already puts folders first so the aggregate lines survive the cut.
- Corpus-level term statistics: the extractive selection weighs terms within one text, because planning touches no store. Document frequency across the index would sharpen both the selection and the keywords (a term common to every file in a folder names nothing); the shape it would take is a snapshot the sweep hands every planner, never a store read per source.
- The width and scope of the summary vector against the source's: whether one vector over a query-shaped summary at a Matryoshka width retrieves as well as vectors over every chunk at the model's native width is an empirical question per corpus, and the benchmark records footprint beside nDCG so the answer is a run, not an argument.
- Folder results in the benchmark: a corpus folder ranks beside its documents, and the harness maps results to document ids, so folder hits take rank slots. Whether the harness should drop `inode/directory` results or the benchmark composition should unmount the directory transform is not decided.
- Recursion into pages: following `text/html` links into fetched pages whose own transforms summarize them. The crawl depth, the follow list, the per-fragment read, and the fragment caps bound it; still missing are a per-source fetch budget (how many references one source may follow at all, independent of depth) and a visited set across sources so fifty documents linking one page fetch it once.
- Content references across the WIT boundary: loaded transforms receive referenced bytes but cannot emit references until the `fragment` record grows the field, which is an ABI change to version.
- Entity deduplication/resolution quality ("Greg" vs "Greg Hunt" vs an email address) — and whether entity resolution is itself a pluggable transform. Keyed sprouts make the plumbing for that pluggable already; the resolution logic is not written.
- Keyed sprouts across the WIT boundary: loaded transforms emit child fragments only today. The entity extractor's shape (key + anchor) is the vocabulary the projection would need. (Embedding-model migration was open here; settled as in-place re-embed in [index-maintenance](index-maintenance.md).)
